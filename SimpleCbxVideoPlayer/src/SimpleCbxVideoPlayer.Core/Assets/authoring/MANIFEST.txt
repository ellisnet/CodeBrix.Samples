================================================================================
MANIFEST: Assets/authoring
The sample-video corpus, file by file - what it is and how it was verified
================================================================================

Written by the corpus generator on 2026-09-02 09:57:24 (local time). Nothing in this
application regenerates the corpus; these files are shipped as data and read from the
output folder. The command lines below name the folder layout the corpus was produced
in, which is the record of how each file was made rather than a path in this
application; the two MP4 originals they read are not carried here.

Every command line below was BUILT by CodeBrix.VideoPlayback.Authoring and RUN by
CodeBrix.VideoProcessing, which launches the host's ffmpeg as a child process. The
generator never invokes ffmpeg itself, and the CodeBrix-Mode2 files are muxed by the
playback library's own bespoke muxer rather than by ffmpeg at all.

WHAT THIS RUN RE-ENCODED: CodeBrix-Mode1.
Everything else below was read back and re-verified, not re-encoded; its command line
is re-derived from the plan, which is where it came from in the first place, and its
encode time is the one the previous manifest recorded.

REPRODUCIBILITY. The SHAPE of this corpus is deterministic - the same twenty-four files,
the same resolutions, the same settings, the same command lines every run. The BYTES
are NOT: the Matroska muxer writes a random track UID and a fresh muxing date into
every file, so two runs of this tool produce files that differ even when the encoder
has made an identical bitstream. Those fields are fixed-length, so the sizes below do
tend to come back the same - but do not pin these files with a hash, and do not treat
a size that moves by a few bytes as a fault. The CodeBrix-Mode2 files carry no random
field at all, but the AV1 encoder is itself only deterministic for a fixed build and
thread count, so the same caution applies to them.

================================================================================
ENCODER SETTINGS, BY RESOLUTION RUNG
================================================================================

  rung   landscape     portrait      preset  crf  keyframes  audio
  -----  ------------  ------------  ------  ---  ---------  ---------
  4k     3840x2160     2160x3840     6       28   60 frames  128 kbit/s
  hd     1920x1080     1080x1920     5       26   60 frames  128 kbit/s
  720p   1280x720      720x1280      4       24   60 frames  96 kbit/s

  Video   libsvtav1, 8-bit yuv420p, 30 frames per second, scaled with lanczos.
  Audio   libopus for MKV, WebM and CodeBrix-Mode1; libvorbis for CodeBrix-Mode2.
          2 channels at 48000 Hz throughout, at the bit rates in the table above.
          The rungs are the SAME numbers for both codecs, so the two ladders stay
          comparable. Mode2 is Vorbis rather than Opus because Mode2 is the flavour an
          application ships inside itself, and a Vorbis file plays with the core
          playback package alone - an Opus one needs the application to add
          CodeBrix.Audio.Opus and call its Register().
  Keyframes every 60 frames is two seconds at 30 frames per second - set
  explicitly, because the encoder's own default interval is far longer and a long
  interval is exactly what makes a scrub feel slow.

  The preset gets FASTER as the frame gets bigger and the rate factor gets LOWER as it
  gets smaller: encode cost scales with the pixel count, and AV1's rate factor is
  resolution-relative, so this keeps both the wall clock and the perceived quality
  roughly level across the three rungs.

CodeBrix-Mode3/ is NOT written by the corpus generator that wrote everything above,
and the totals above do not count it. It was authored on 2026-10-22, from the same
two Public-Domain originals, by a one-off program driving
CodeBrix.VideoPlayback.Authoring 1.0.290.1224's MASTER flavour (CbvAuthor.Write
with Flavour = VideoAuthoringFlavour.Master). Every command it ran is recorded below,
file by file; that is the record to reproduce the folder from.

WHAT A MASTER IS. The bespoke CBVF container at format version 1: AV1 picture, an
optional alpha-plane track (the picture's alpha channel as monochrome, full-range
AV1, in lock step with the picture), and lossless FLAC sound.

ENCODER SETTINGS. The corpus's own rungs, applied to the master flavour's IN-PROCESS
encoders rather than to libsvtav1:

  rung   landscape     portrait      cpu-used  cq-level  keyframes  audio
  -----  ------------  ------------  --------  --------  ---------  ------------------
  4k     3840x2160     2160x3840     6         28        60 frames  FLAC 16-bit lossless
  hd     1920x1080     1080x1920     5         26        60 frames  FLAC 16-bit lossless
  720p   1280x720      720x1280      4         24        60 frames  FLAC 16-bit lossless

  Video   the authoring library's in-process AV1 encoder (the libaom reference
          encoder), good-quality usage, 8-bit 4:2:0, 30 frames per second. The
          preset column above becomes cpu-used and the crf column cq-level - the
          same 0-63 scale, though libaom and libsvtav1 do not give identical
          quality at the same number. The six plain files are scaled by the
          library's own FFmpeg prepare pass (lanczos, accurate rounding, full chroma
          interpolation) into a lossless FFV1 intermediate first.
  Alpha   the two _alpha files only: the same encoder, monochrome and full range,
          at cq-level 20 (six better than the picture), with a key frame forced on
          every key frame of the picture. Fully transparent pixels take the colour of
          the nearest visible one before the picture is encoded (the library's
          transparent-pixel fill), so no dark fringe bleeds into a soft edge.
  Audio   the recording's AAC decoded at 48000 Hz stereo and encoded as FLAC,
          16-bit, compression level 5: from there on, nothing is lost.

THE MATTE. The two _alpha sources are made first, by FFmpeg, as a lossless FFV1
(yuva420p) Matroska file with PCM sound: the recording scaled to HD at 30 frames per
second, with a one-frame grey image merged in as its alpha channel. The image is

    alpha = 255 * clip((1 - r) / 0.25, 0, 1),
    r     = hypot((x - W/2) / (W/2), (y - H/2) / (H/2))

- fully opaque inside three-quarters of the ellipse that touches the picture's four
edges, fading to fully transparent at that ellipse, and fully transparent in the
corners beyond it. The merge stops with the last whole picture frame, so the two
_alpha files are one frame (33 ms) shorter than the plain ones.
